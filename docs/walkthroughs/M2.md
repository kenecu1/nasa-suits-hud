# M2 walkthrough: telemetry, caution and warning, low-light design

Branch `SUITS-56-m2-telemetry-alerts`. Session 1 (backend, contract, data) built 2026-11-23/24. Session 2 (client and end to end) built 2026-11-24. The session-1 notes are kept at the end of this file.

## What was built

The HUD now shows every suit value, raises clear alerts with NASA's recommended action, plays a tone on a new warning, and takes its first input from the wearer. The backend decides every level, alert, order and severity (session 1); the client only draws.

- **Panels** (`client/src/scene/`), placed by `hud/layout.ts` around the clear centre: the **alert banner** top centre (`AlertBanner.tsx`, at most 3 rows plus "+N MORE"), **status** top left (`StatusPanel.tsx`: EVA clock and link line), **vitals** left (`VitalsPanel.tsx`: heart rate and temperature, larger while off-nominal), **switches** lower left (`SwitchPanel.tsx`: DCU and UIA), **consumables** lower right (`ConsumablesPanel.tsx`: 7 bars with a mark at the warning limit), and the **details page** (`DetailsPage.tsx`: all 23 values in groups, in two panels that take the place of vitals, switches and consumables while open).
- **View models** (`client/src/hud/*.vm.ts`, pure, vitest): `banner`, `tone`, `consumables`, `vitals`, `switches`, `details`, `clock`, `link`, built together by `hud.ts`. `values.ts` reads one value (unknown and stale rules, formatting); `layout.ts` holds the panel boxes and the exact geometry; `contrast.ts` the WCAG maths.
- **Theme** (`client/src/theme.ts`): text sizes in dmm (minimum 24 dmm = 28.8 panel pixels at 1.2 m), the low-light palette of decision F, the panel backing at opacity 0.92, one style per level (colour, shape, word), now six levels with `off`.
- **Input** (`client/src/input/`): `intents.ts` holds the `Intent` type and one table per device (keyboard: A = `ack_alert`, D = `toggle_details`; right controller: A and B). `keyboard.ts` and `XrButtons.tsx` are the only listeners. `dispatch.ts` turns an intent into a command and hands it to `net/link.ts`, whose new `send()` drops a command (with a console warning and `input.dropped`) unless the link is live and the socket open.
- **Tone**: `tone.vm.ts` says when a warning id is new; `store.ts` counts it once per state; `scene/Tone.tsx` plays it through `scene/audio.ts` (Web Audio, unlocked by the first key or click).
- **The `off` level** (approved by Vlad for session 2): the fan the DCU FAN switch does not select reads 0 rpm by NASA's rule; the backend now gives it level `off` (`active_when` in `data/ranges.json`, read by `core/store.py`), drawn dimmed with a dash and the word OFF.
- **End to end** (`e2e/`): desktop screenshots for nominal, caution, warning, link lost, EVA not started, details and offline; keys A and D through to the backend; decision B with two alerts; the emulated headset with controller A and B; draw calls.

## How data flows: the fan fails, the wearer acknowledges, the fan is switched

```mermaid
sequenceDiagram
  participant D as sim/dynamics.py + scenarios.py
  participant T as sim/fake_tss.py (UDP)
  participant S as tss/legacy.py + mapping.py + source.py
  participant P as core/publisher.py
  participant C as core/store.py + alerts.py
  participant A as app.py /ws + core/commands.py
  participant N as net/link.ts + parse.ts
  participant Z as store.ts
  participant V as hud/banner.vm.ts + tone.vm.ts
  participant G as scene/AlertBanner.tsx + Tone.tsx + audio.ts
  participant I as input/keyboard.ts or XrButtons.tsx + dispatch.ts + intents.ts

  D->>T: fault fan: fan_pri_rpm winds down, error.fan_error true
  S->>T: GET telemetry (legacy port, one at a time)
  T-->>S: JSON, fan_pri_rpm 21500, all 23 names present
  S->>P: on_change (arrival #812)
  P->>C: observe(snapshot): fan_pri_rpm warning, fan_sec_rpm off; AlertBook sample 1 of 2
  S->>P: next telemetry, arrival #813
  P->>C: observe: sample 2 of 2, alert "fan" raised, unacked
  P->>A: preview() → State with alerts[0] = fan warning
  A->>N: JSON text over /ws
  N->>Z: parseState → receive(state): prev kept, buildHud(state, live, prev)
  Z->>V: bannerVm: row triangle WARNING "DCU FAN to SEC, return to lander", topId "fan"; toneVm: new warning id
  Z->>Z: toneCount + 1 (once for this state)
  Z->>G: AlertBanner draws the row; Tone sees the count rise, audio.beep()
  I->>Z: key A (KeyA) or controller A (button 4) → intent ack_alert → commandFor reads banner.topId
  I->>N: link.send({"type":"command","name":"ack_alert","args":{"id":"fan"}})
  N->>A: command JSON (socket open and link live, else dropped with a warning)
  A->>C: commands.dispatch → Store.ack("fan") → AlertBook acked
  C->>P: notify_change
  P->>A: State with alerts[0].acked = true, about 100 ms later
  A->>N: JSON text
  N->>Z: receive: banner row ACK, action dimmed; no new warning, no tone
  Note over D,G: later the wearer sets DCU FAN to SEC: fan_sec_rpm 30000 nominal, fan_pri_rpm becomes off, 3 nominal samples clear the alert and the row disappears
```

The client never changes the banner on its own: after a key press it waits for the backend's next `State`. A command pressed while offline is dropped, not queued.

## What differs from `docs/briefs/M2.md`, and why

1. **New level `off`** (Vlad's decision for session 2, not in the brief). Contract `Level` gained `off`; `data/ranges.json` marks each fan with `active_when` (DCU switch and position); `core/store.py` gives the unselected fan `off` after the unknown and stale checks, and only while the DCU position is fresh. Only the fans; the fan alert rule is unchanged. Tests in `backend/tests/core/test_store.py` (PRI and SEC, the active fan failing or at 0 rpm stays a warning, unknown DCU, stale and unknown win, no alert, a bad `active_when` refused at load). The mapping lives in `ranges.json`, not in `store.py`, because the import-boundary test forbids TSS names in `core/`.
2. **Controller buttons are read from raw WebXR gamepads** (`input/XrButtons.tsx`), not `useXRControllerButtonEvent`, and `scene/xr.ts` keeps `controller: false`. The library's controller state downloads its input profile from a CDN, which tests may not do (`docs/notes/xr-controller-buttons-without-profiles.md`). Bindings: right A (index 4) = `ack_alert`, right B (index 5) = `toggle_details`. A button already held when the session starts does not fire.
3. **Keys**: A acknowledges, D opens and closes the details page.
4. **Layout** (`hud/layout.ts`): side panels at ±27.5°, 470 px wide; banner top centre, 600 px. Battery moved from "top left" (archive sketch) into consumables. The **details page** is two panels left and right of the centre that replace vitals, switches and consumables while open; 23 rows do not fit anywhere else outside the clear centre at 24 dmm. The **laptop camera** widened from 50° to 70° so all panels fit a 1280 × 720 picture; the headset is unaffected.
5. **Acceptance 8 is checked by exact geometry.** `layout.ts` places each corner exactly as `PanelAt.tsx` does, measures pitch along the edges (a straight edge peaks between its corners), and also checks that every panel fits the laptop picture and both emulated eyes. `ViewProbe.tsx` checks the same corners in the running page for every panel shown (`panelsShown`, `panelsOutOfView`). Angles alone understated how far corners land (`docs/notes/xr-panel-corners-project-wider.md`).
6. **Consumables show 7 bars**: both oxygen tanks, both batteries, both scrubbers, coolant. The battery PRI/SEC switch is not in the DCU packet, and picking "the active scrubber" in the client would be a mission rule. The mark sits at the **warning limit** only (min for values checked low, max for values checked high).
7. **The client reads `data/ranges.json`** (same file as the backend) for two drawing choices only: where the limit mark goes, and which way to round. Rounding never makes a value look inside its limit: below the minimum it goes down, above the maximum up (49.6 bpm reads "49 bpm", not "50"). The level still comes only from the backend.
8. **No word beside a nominal value** in rows (consumables, vitals, details): seven green "NOMINAL"s would be noise. Nominal still has its circle and colour; every other level adds its word. Banner rows always show their word.
9. **The tone is counted in the store** (`toneCount`), not only flagged in the view model, so it is neither lost when two states arrive before React draws nor repeated when the scene is rebuilt. Browsers lock audio until a key press or click; a warning that arrives before then is counted as missed (`window.__hud.tonesMissed`) and logged, not queued to sound late.
10. **Acceptance 12** uses M2's limit of 100 draw calls (M1's test had 50). Measured: laptop 26 with every closed-mode panel and a banner, 37 with the details page open; emulated headset 44 and 76 (two eyes).
11. **Screenshots**: M1's `live` baseline became `nominal`; new baselines for caution, warning, link-lost, eva-not-started, details, and `warning-in-session` in the headset. The M1 `in-session` baseline still passed at 2% after the whole layout changed, so it was refreshed explicitly (`docs/notes/e2e-dark-screenshots-pass-at-two-percent.md`).
12. **New scenario `fan_then_oxygen`** for the brief's question 1 (decision B with two alerts end to end).
13. **Removed** `hud/o2.vm.ts` and `hud/dcu.vm.ts` (M1): consumables and switches replace them. The status panel draws two view models (clock and link).
14. **Not built**: the archive sketch's flashing side icons. The banner is static text; the tone carries the urgency.

## Reviews (session 2)

Ran `ecc:silent-failure-hunter`, `ecc:typescript-reviewer`, `ecc:react-reviewer` and `ecc:pr-test-analyzer` on this session's diff.

Fixed, with tests: a command "sent" into a closing socket (the link stays live up to 3 s after the socket goes); the tone lost when two states land before a render, repeated after a scene rebuild, queued while audio is locked, and counted before it played; a controller button already held at session start firing A or B; an intent error re-firing every frame; a failed view probe leaving "in view" standing (`probeError`); rounding that showed 49.6 bpm as "50"; pitch measured only at corners; `commandFor` sending `toggle_details` for any future intent (now exhaustive); the panel backing rebuilt on every render; banner wording and colours chosen in components. Added tests for decision B with two alerts, the tone in the headset, the active fan at 0 rpm, unknown and off consumables, the shape of `ranges.json`, and a source check that components hold no literal sizes or colours and listen to no keys.

Left, with reasons:
- **No on-screen "not sent" cue.** A press while offline is dropped with a console warning and counted in `window.__hud.input.dropped`; the link line already says OFFLINE. A visible cue can come with M6 (voice), which needs the same feedback.
- **Clipped content is not detected.** Panels have fixed boxes with `overflow="hidden"`; a longer text or an extra row would be cut silently. The boxes were sized from the screenshots; `docs/notes/ui-uikit-text-wraps-by-default.md` says how. Worth a measured check when M3 adds procedure text.
- **Every panel re-renders once a second** (new view-model objects per state). Cheap at 1 Hz; structural sharing can come if the headset frame rate suffers (M9).
- **`ViewProbe` and `window.__hud` run in every build.** Small cost per frame; gate them before the headset demo if needed.
- **The 2% screenshot tolerance** stays as CLAUDE.md sets it; the note explains how to refresh baselines on purpose.
- **An alert with an empty id** would make A acknowledge the backend's own top. The backend always sets ids.
- **The emulated headset runs a subset of the laptop checks** (warning, acknowledgement, details, tone, panels in view), not all five screenshot states.

### What differs from `docs/briefs/M2.md`, and why

1. **Client test fixtures changed.** The three new `State` fields are required in the generated types, so six client test files that build a `State` by hand gained `link.level`, `alerts: []` and `ui`. Vlad approved this in session; no client source changed.
2. **`Store.observe()` beside `preview()`.** The publisher calls `observe(snapshot)` (advances the AlertBook), then `preview(snapshot)` (pure). Brief section 8 sketched `step(book, inputs, now) → (book, alerts)`; the code has `step(book, inputs, rules) → book` and `book.alerts()`, with time in `inputs.t`. Same idea: all memory is in the value.
3. **Arrivals between two steps all count** (up to 3). An unchanged telemetry reply wakes nobody, so the publisher may only see it at the next 1 s heartbeat. Counting only "changed since last step" would have made an alert with steady values never clear. Found by `ecc:python-reviewer`.
4. **A sample with an unknown input can raise but never clear.** "Nominal" needs every input known, including the switch-selected one (fan, scrubber) while the DCU position is unknown. A held alert keeps its last off-nominal title instead of naming a healthy value.
5. **Escalation:** a caution becomes a warning after 2 warning samples and is unacknowledged again; it falls back to caution after 3 samples without warning. `since` and the id stay.
6. **Link alert texts are ours** (`data/alerts.json`): `unreachable`, `unassigned`, `bad_data` (warnings), and `stale` → caution "SUIT DATA OLD" only when telemetry is old while the TSS is still heard. An old status or fault section alone (normal for ~7 s after start) raises nothing.
7. **Battery rule watches both batteries.** The battery PRI/SEC switch is not in the DCU packet (`docs/notes/tss-dcu-switch-meaning.md`), so it cannot watch "the active one" like fan and scrubber. A depleted battery stays listed after switching (acknowledged, it sinks). NASA's power flag, which knows the battery, clears.
8. **Extra scenarios for session 2's screenshots:** `eva_not_started` and `heart_rate_high` (caution), besides the spec's three. `SUITS_SCENARIO=<name>` (sim only) and `SUITS_SCENARIO_SPEED` play one on `npm run dev`. `link_loss` loses the link at 8 s, after the link has settled.
9. **Allowed origins:** localhost, 127.0.0.1 and [::1], http and https, on `SUITS_CLIENT_PORT` (5173) and `SUITS_E2E_CLIENT_PORT` (5183), plus `SUITS_ALLOWED_ORIGINS`. The headset's address must be listed there.
10. **The fake follows NASA's fan rule: only the active fan spins.** So `fan_sec_rpm` reads 0 with level `warning` in `suit.values` while the primary fan runs (no alert: the fan rule watches only the active fan). **For session 2:** the details page and vitals will show "FAN SEC 0 rpm" in warning style unless something marks the inactive device. That needs a backend/contract decision (Kenny and Vlad), not a client rule.
11. **Fault rates in `sim/dynamics.py` are ours** (per second of scenario time). NASA's are per simulation tick and its fault logic is off at the pinned commit.

### Review findings not fixed (session-1 helper reviews)

Fixed with tests: arrival counting (3 above), held alerts and titles with an unknown DCU (4), a rule file naming one value twice, log-line injection through unknown command keys, a scenario step retried every tick on failure, scenario `set` typos and keys the fault rules overwrite, a sim loop that could fail forever without `/health` noticing, `SUITS_SCENARIO_SPEED` without a scenario, origins with a path or capitals, big WebSocket frames in `npm run dev` (`--ws-max-size 65536`).

Left, with reasons:
- **A name that arrives with a non-number is not "missing".** Decision A is about absent names. It shows as `unknown` and blocks the all-clear of its problem (4), so it cannot hide an alert.
- **A stale fault section clears fault alerts.** Faults arrive about every 7 s and go stale at 15 s, so this needs a real link problem, which raises its own alert.
- **A stale DCU has no alert of its own.** The fan and scrubber problems hold instead (4). A "DCU DATA OLD" caution can come later if it matters.
- **A decode error is hidden behind the data alert** while names are also missing (`bad_data` link alert is suppressed then, to keep one row per problem).
- **No rate limit or connection cap on `/ws`,** one log line per bad frame. Acceptable for a local tool; clients without `Origin` are allowed by design.
- **The e2e backend (`e2e/support/backend.ts`) has no `--ws-max-size`.** That file is session 2's.
- **Port 5183 is allowed in every run,** as the brief asks ("plus the test port").
- **`send_states` catches only `WebSocketDisconnect`** (M1 code; no failure seen in 630 runs).
- **The State is built three times per publish** (observe, preview). 23 values; not worth the extra API.
- **`AlertBook` holds dicts inside a frozen dataclass.** Immutable by convention; every function builds new dicts.
- **FastAPI's `/docs` page is on.** It only shows the routes.

Not run: the optional live TSS check (review gate 3).
