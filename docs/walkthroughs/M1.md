# M1 walkthrough: walking skeleton

One suit value (primary oxygen) and one switch (DCU oxygen) travel from the TSS to a WebGL panel, on the laptop page and inside an emulated headset. Branch `SUITS-55-m1-walking-skeleton`. Built 2026-11-16 in two sessions.

## What was built

- **Backend (session 1, parts 1–6):** the TSS adapter (`backend/suits/tss/`), a fake TSS (`sim/fake_tss.py`), recorder and replayer, contract v2, and the app with `/ws` and `/health` in modes `sim`, `replay` and `live`.
- **Client (session 2, part 7), `client/src/`:**
  - `net/link.ts`: one WebSocket, reconnect with backoff (0.5, 1, 2, 4, then 5 s), and a silence watchdog (no usable state for 3 s means offline). `net/parse.ts` checks a message is a contract v2 state. `net/backendUrl.ts` derives `ws://<page>/ws` from the page address; the dev server forwards it to the backend.
  - `store.ts`: the last `State`, the connection status, and the view models built from the two.
  - `hud/o2.vm.ts`, `dcu.vm.ts`, `link.vm.ts`: pure functions, state in, text and look out. `theme.ts` holds every colour, size, shape and word.
  - `scene/`: `HudRig.tsx` (follows the head, arithmetic in `rigMath.ts`), `StatusPanel.tsx` (uikit panel), `LevelShape.tsx`, `ViewProbe.tsx` (measures what was drawn), `xr.ts` and `emulator.ts`.
  - `App.tsx`: the start bar with the Enter AR button (HTML, outside the headset view). `testHook.ts`: `window.__hud`.
- **End-to-end (part 8):** `playwright.config.ts`, `e2e/desktop/hud.spec.ts`, `e2e/xr/headset.spec.ts`. The tests start and stop the backend themselves (`e2e/support/backend.ts`).
- **Smoke script (part 9):** `scripts/tss_smoke.py`, tested against the fake TSS in `backend/tests/test_tss_smoke.py`.

## How data flows: someone flips the oxygen switch

```mermaid
sequenceDiagram
    participant TSS as TSS (or fake_tss.py)
    participant Sub as tss/subscription.py
    participant Src as tss/source.py<br/>(codec.py, mapping.py)
    participant Core as core/store.py<br/>core/publisher.py
    participant App as app.py /ws
    participant Link as net/link.ts<br/>(parse.ts)
    participant Store as store.ts<br/>(hud/dcu.vm.ts)
    participant Panel as scene/StatusPanel.tsx
    TSS->>Sub: DCU packet, UDP 14141 (pushed once a second)
    Sub->>Src: feed(datagram)
    Src->>Src: check checksum, decode, flag 0 becomes "SEC"
    Src->>Core: changed
    Core->>Core: wait about 100 ms, build State (seq + 1)
    Core->>App: State
    App->>Link: JSON text over WebSocket (through the dev server's /ws)
    Link->>Link: parseState: type "state", v 2
    Link->>Store: receive(state), then status "live"
    Store->>Store: buildHud(state, conn): dcu.text "SEC"
    Store->>Panel: React re-renders the text
    Store-->>Store: testHook.ts copies panels to window.__hud
```

If the backend dies, `link.ts` sees the socket close (or 3 s of silence), sets the status to `offline`, and `buildHud` runs again with the same state: oxygen becomes `92% STALE` with a square, the switch turns to the stale colour, and the link line says `OFFLINE` with a red triangle. The number stays; nothing stays green.

## What differs from `docs/briefs/M1.md`, and why

1. **Fable 5.2 built session 2, and there is no Fable review.** Section 12 says Opus builds and Fable reviews. Vlad changed this for session 2 (Fable access ends 2026-11-16). Session 2 is to be reviewed in a fresh Opus chat.
2. **Legacy polling is slower than planned (session 1).** The spec says poll telemetry, status and faults once a second. The real TSS serves about one request per team port every 1.2 s, so the poller sends one request at a time and, after a missed reply, waits one more 2 s window before the next (commit `fbd2d64`). Measured: telemetry every 1.0–3.3 s, status and faults about every 7 s. See `docs/notes/tss-legacy-port-is-slow.md`.
3. **The docs helper could not reach Context7** (its tool names do not match this plugin). The builder queried Context7 directly and checked the installed packages instead.
4. **The emulator is installed by our own code.** The built-in emulator of `@react-three/xr` does not install in Chromium with iwer 2.8, and its control panel needed one shared three.js. See the two `xr-` notes.
5. **The backend address uses the dev server's proxy** (`/ws` on the page's own origin), not a second port. The headset then needs only one address.
6. **Three view models, one panel:** oxygen, switch and link each have a view model; `window.__hud.panels` has `o2`, `dcu` and `link`.
7. **No intents yet.** M1 has no user action that becomes a command. Enter AR is a plain button because a browser only starts a session from a click.
8. **Oxygen percent is floored, not rounded,** so 19.6 never reads "20%" when 20 is the limit.

## Not done, said plainly

- **Acceptance 16, in part.** `npm run tss:smoke` was not run against a real TSS in session 2. The script is tested against the fake TSS only. The real 60 s recording from session 1 (`data/recordings/real-tss-6293795.jsonl`) exists and is the replay fixture.
- **End-of-session reviews not run:** `ecc:typescript-reviewer`, `ecc:react-reviewer`, `ecc:pr-test-analyzer` (usage ran out). `ecc:silent-failure-hunter` did run; its one high finding and five smaller ones are fixed with tests (commit `b2ed195`).
- **Known limits from that review, not fixed:** `OFFLINE` does not say why (a wrong contract version looks like a dead backend; the reason is only in the console). A backend that keeps re-sending one frozen state looks live. After the laptop wakes from sleep, an old state can show as live until the watchdog timer fires.
- One unit test from the test helper had a bug in its own helper (`makeState(undefined)` used the default value). The helper call was fixed; no assertion was changed.

## Three things to try

1. Run the two halves in two terminals: `.venv\Scripts\python -m uvicorn --factory suits.app:create_app --port 8000` and `npm run dev --workspace client`. Open `http://localhost:5173`. Stop the backend with Ctrl+C and watch the panel go stale and `OFFLINE`. Start it again and watch the page recover without a reload.
2. On the same page press **Enter AR**. In the emulator panel change the headset rotation and watch the panel follow after a short delay. Read `window.__hud.view` in the browser console.
3. In `client/src/theme.ts` change `rig.followS` from 0.35 to 2 and repeat step 2. Then run `npm run e2e -- --project=xr` and see which assertion notices.

## Three questions you should be able to answer

1. The backend process is killed. Which file notices first, what are the two ways it can notice, and why does the oxygen number stay on screen but change shape and colour?
2. Why does the client ignore `seq`, and what would the wearer see after a backend restart if it dropped messages with a lower `seq`?
3. The headset test cannot read text from the DOM. How does it know the panel is inside the view after the head turns, and why does it also check that the panel was *out* of view for a moment?
