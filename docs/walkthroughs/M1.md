# M1 walkthrough: walking skeleton

One suit value (primary oxygen) and one switch (DCU oxygen) travel from the TSS to a WebGL panel, on the laptop page and inside an emulated headset. Branch `SUITS-55-m1-walking-skeleton`. Built 2026-11-16 in two sessions.

## What was built

- **Backend (session 1, parts 1–6):** the TSS adapter (`backend/suits/tss/`), a fake TSS (`sim/fake_tss.py`), recorder and replayer, contract v2, and the app with `/ws` and `/health` in modes `sim`, `replay` and `live`.
- **Client (session 2, part 7), `client/src/`:**
  - `net/link.ts`: one WebSocket, reconnect with backoff (0.5, 1, 2, 4, then 5 s), and a silence watchdog (no usable state for 3 s means offline). `net/parse.ts` checks a message is a contract v2 state. `net/backendUrl.ts` derives `ws://<page>/ws` from the page address; the dev server forwards it to the backend.
  - `store.ts`: the last `State`, the connection status, and the view models built from the two.
  - `hud/o2.vm.ts`, `dcu.vm.ts`, `link.vm.ts`: pure functions, state in, text and look out. `theme.ts` holds every colour, size, shape and word.
  - `scene/`: `HudRig.tsx` (follows the head, arithmetic in `rigMath.ts`), `StatusPanel.tsx` (uikit panel), `LevelShape.tsx`, `ViewProbe.tsx` (measures what was drawn), `xr.ts` and `emulator.ts`.
  - `App.tsx`: the start bar with the Enter AR button (HTML, outside the headset view). `SceneBoundary.tsx`: rebuilds the HUD if drawing it throws. `testHook.ts`: `window.__hud`.
- **End-to-end (part 8):** `playwright.config.ts`, `e2e/desktop/hud.spec.ts`, `e2e/xr/headset.spec.ts`. The tests start and stop the backend themselves (`e2e/support/backend.ts`).
- **Smoke script (part 9):** `scripts/tss_smoke.py`, tested against the fake TSS in `backend/tests/test_tss_smoke.py` and run against the real TSS.

## How data flows: someone flips the oxygen switch

```mermaid
sequenceDiagram
    participant TSS as TSS (or fake_tss.py)
    participant Sub as tss/subscription.py
    participant Src as tss/source.py<br/>(codec.py, mapping.py)
    participant Core as core/store.py<br/>core/publisher.py
    participant App as app.py /ws
    participant Link as net/link.ts<br/>(parse.ts)
    participant Store as store.ts<br/>(hud/dcu.vm.ts)
    participant Panel as scene/StatusPanel.tsx
    TSS->>Sub: DCU packet, UDP 14141 (pushed once a second)
    Sub->>Src: feed(datagram)
    Src->>Src: check checksum, decode, flag 0 becomes "SEC"
    Src->>Core: changed
    Core->>Core: wait about 100 ms, build State (seq + 1)
    Core->>App: State
    App->>Link: JSON text over WebSocket (through the dev server's /ws)
    Link->>Link: parseState: type "state", v 2
    Link->>Store: receive(state), then status "live"
    Store->>Store: buildHud(state, conn): dcu.text "SEC"
    Store->>Panel: React re-renders the text
    Store-->>Store: testHook.ts copies panels to window.__hud
```

If the backend dies, `link.ts` sees the socket close (or 3 s of silence), sets the status to `offline`, and `buildHud` runs again with the same state: oxygen becomes `92% STALE` with a square, the switch turns to the stale colour, and the link line says `OFFLINE` with a red triangle. The number stays; nothing stays green.

## What differs from `docs/briefs/M1.md`, and why

1. **Fable 5.2 built session 2, and there is no Fable review.** Section 12 says Opus builds and Fable reviews. Vlad changed this for session 2 (Fable access ended 2026-11-16). From 2026-11-22 every milestone is built and reviewed by Opus 5.5 in its own session, with no separate review chat ("How milestones are reviewed" in `docs/plan/README.md`). M1's deep review ran under that rule on 2026-11-22 (see Reviews below).
2. **Legacy polling is slower than planned (session 1).** The spec says poll telemetry, status and faults once a second. The real TSS serves about one request per team port every 1.2 s, so the poller sends one request at a time and, after a missed reply, waits one more 2 s window before the next (commit `fbd2d64`). Measured: telemetry every 1.0–3.3 s, status and faults about every 7 s. See `docs/notes/tss-legacy-port-is-slow.md`.
3. **The docs helper could not reach Context7** (its tool names do not match this plugin). The builder queried Context7 directly and checked the installed packages instead.
4. **The emulator is installed by our own code.** The built-in emulator of `@react-three/xr` does not install in Chromium with iwer 2.8, and its control panel needed one shared three.js. See the two `xr-` notes.
5. **The backend address uses the dev server's proxy** (`/ws` on the page's own origin), not a second port. The headset then needs only one address.
6. **Three view models, one panel:** oxygen, switch and link each have a view model; `window.__hud.panels` has `o2`, `dcu` and `link`.
7. **No intents yet.** M1 has no user action that becomes a command. Enter AR is a plain button because a browser only starts a session from a click.
8. **Oxygen percent is floored, not rounded,** so 19.6 never reads "20%" when 20 is the limit.

## Reviews and the real TSS

- **Acceptance 16 passes.** `npm run tss:smoke` was run against the real TSS in WSL (commit 6293795, team 0) on 2026-11-16. 5 s: DCU, UIA and all 23 telemetry values decoded, exit code 0. 15 s: faults too, `link: ok`. `--record` wrote its own file and left the committed fixture alone. The 60 s recording from session 1 (`data/recordings/real-tss-6293795.jsonl`) stays the replay fixture.
- **That run changed the script.** The first version failed a healthy link, because it wanted `link: ok` after 5 s and the real TSS sends faults only about every 7 s. The verdict now judges what the spec names: DCU, UIA and telemetry received and still fresh, and the link not `unassigned`, `unreachable` or `bad_data`.
- **Helper reviews, all run, none found anything critical:**
  - `ecc:silent-failure-hunter`: one high finding (a state that cannot be applied kept the link "live") and five smaller ones, fixed with tests (`b2ed195`).
  - `ecc:react-reviewer`: one high finding (the error boundary sat outside the canvas, so a crash during a headset session left a dead session). The boundary is now inside the canvas, and waits longer after each failure in a row.
  - `ecc:typescript-reviewer`: no high findings. The end-to-end backend helper can no longer hang on stop, crash on a failed spawn, or attach to a backend left over from an earlier run.
  - `ecc:pr-test-analyzer`: acceptance 11 to 15 proved, nothing weakened. Its main point, that a page with "92%" hard-coded would pass, is closed by a new test that replays the real recording (oxygen about 90% and falling).
  - Fixes for the last three are in `f94ac82`.
- **Deep review (Opus 5.5 subagent, 2026-11-22):** "sound enough to build M2 on". No high findings, and every acceptance item 1–15 has a test that would fail if the behaviour broke. Fixed:
  - A new `npm run tss:smoke -- --record` file (`real-tss-<commit>.jsonl`) would have broken `npm run check`, because the replay test globbed every such file. The fixtures are now listed by name (`backend/tests/tss/test_replay.py`).
  - The import-boundary test blocked only codec, subscription and legacy. It is now an allow-list: outside `tss/` and `sim/` only `suits.tss.client`, `source` and `recorder` may be imported, so `mapping` and `transport` are private too.
  - While the link was `unreachable` (2.5 s), oxygen could still read green until its own 4 s stale limit. Now every suit value is stale as soon as the link is unreachable (`core/store.py`, with a test).
  - The HUD crash guard never reset its failure count, so after five unrelated crashes in a long EVA every rebuild waited 30 s. A rebuild that runs 60 s now starts the count again.
  - Listed for M2, not fixed: see "For M2" below.
- One unit test from the test helper had a bug in its own helper (`makeState(undefined)` used the default value). The helper call was fixed; no assertion was changed. The test analysis agrees.

## Known limits, not fixed

- `OFFLINE` does not say why: a wrong contract version looks like a dead backend, and the reason is only in the browser console.
- A backend that keeps re-sending one frozen state looks live. Catching that is the backend's job.
- After the laptop wakes from sleep, an old state can show as live until the watchdog timer fires.
- The error boundary has no automated test (only its wait times are tested). Forcing a render error needs a hook the page does not have.
- CI retries stay at 0, and the 4 s offline limit and the 2 s wait after the head turn are the acceptance numbers, kept as they are. If CI on Linux proves slow, look at these first.
- The crash guard's new 60 s reset has no automated test either, for the same reason.

## For M2 (from the deep review)

- **Expected but missing must be a fault.** TSS field names are the keys all the way to the client. If NASA renames `oxy_pri_storage`, the HUD shows "NO DATA" while the link says OK, and `tss:smoke` still passes. The adapter should check the expected names arrive (report `bad_data`, fail the smoke), and ideally map TSS names to our own inside `tss/`.
- **Severity from the backend.** `client/src/hud/link.vm.ts` decides that `unreachable` and `unassigned` are warnings. When M2 adds alerts, the backend should send severity in `State` and view models should only map it to the theme.
- **Check `Origin` before `/ws` accepts commands.** `npm run dev` binds the backend to `0.0.0.0`, and WebSockets are not covered by CORS.
- Low, self-healing: an Ack carries no device id, so a late DCU Ack can be taken for UIA's; UIA then arrives about 3 s late. Low, for M8: the fake TSS's `legacy_gets` and rebind task lists grow for as long as sim mode runs.

## Three questions you should be able to answer

1. The backend process is killed. Which file notices first, what are the two ways it can notice, and why does the oxygen number stay on screen but change shape and colour?
2. Why does the client ignore `seq`, and what would the wearer see after a backend restart if it dropped messages with a lower `seq`?
3. The headset test cannot read text from the DOM. How does it know the panel is inside the view after the head turns, and why does it also check that the panel was *out* of view for a moment?
